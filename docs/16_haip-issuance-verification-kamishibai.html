第9話・その1

HAIP は「素の流れ」に 何を足すのか

✦✦

はいぷ先生第7話(発行)と第8話(検証)は「素の OID4VCI / OID4VP」の流れ。第9話では、そこに HAIP(高保証プロファイル)が「銀行なみのきびしさ」を上乗せすると、どこがどう変わるかを見ていくよ。

おとなのことばHAIP は素の仕様の「たくさんの選択肢」から採用オプションを1つに絞り、必須化するプロファイル。ここでは発行(VC)側と検証(VP)側で「素 → HAIP」の差分を対比します。出典は HAIP 1.0(errata set 1)。
第9話・その2

上乗せの 全体像(発行側・検証側)

  • 発行
    FAPI2準拠(PAR＋PKCE＋iss)／DPoP／Wallet Attestation／Key Attestation「本人＋正規ウォレット＋安全な鍵」を厳格に
  • 共通
    フォーマット dc+sd-jwt・mso_mdoc／署名 ES256／ハッシュ SHA-256アルゴリズムを固定
  • 検証
    署名付きリクエスト(JAR)＋x509_hash／DCQL必須／direct_post.jwt(暗号化)／エフェメラル鍵なりすまし・盗み見・追跡を防ぐ
  • 失効
    Token Status List で失効管理
おとなのことば大別すると「①選択肢を絞る(相互運用)」「②新規に必須化(セキュリティ)」「③具体値を固定(実装差の排除)」。次ページから発行側→検証側の順で対比します。
HAIP・発行①

認可を「銀行ルール(FAPI2)」で固める

素の OID4VCI → HAIP
# 素:PAR は「推奨」、PKCE は「推奨」、iss は規定なし
# HAIP:FAPI2 Security Profile 準拠が MUST
  POST /par            # ← 必須(裏口から先に登録)
  code_challenge_method=S256   # ← PKCE 必須
  ...?code=...&iss=https://as.example.com  # ← iss 必須

はいぷ先生第4話でやった PAR・PKCE・iss は、素だと「推奨」どまり。HAIP は「FAPI2 に準拠せよ(MUST)」として、これらをまとめて必須にするんだ。

おとなのことばHAIP:「FAPI2 Security Profile の該当条項に準拠(MUST)」。素の OID4VCI では PAR/PKCE は RECOMMENDED、iss は規定なし。詳細フローは第4話(docs/11)。
HAIP・発行②

きっぷを「鍵の持ち主だけ」使えるように(DPoP)

トークン取得時に DPoP を付ける
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIs...  # 鍵で署名した証明
→ 返るトークン: "token_type": "DPoP", cnf.jkt=鍵の指紋

はいぷ先生素だと Bearer(だれでも使えるきっぷ)。HAIP は DPoP で「鍵を持つ本人だけが使えるきっぷ」にする。盗まれても使えない!

おとなのことばHAIP:DPoP(RFC9449)による送信者制約トークンが MUST。素の OID4VCI では DPoP は任意。詳細は第4話。
HAIP・発行③

「正規ウォレット」と「安全な鍵」を証明させる

HAIP が発行時に追加で求めること
  • Wallet Attestation:「これは正規のウォレットです」の証明(x5c)でクライアント認証
  • Key Attestation:proof の鍵が金庫(セキュアな領域)で作られ保管されている証明
  • proof は jwt と attestation の両対応、nonce_endpoint 必須

はいぷ先生素だと proof は「鍵を持ってる」だけ示せばOK。HAIP は「そのウォレットは正規品?」「鍵はちゃんと金庫の中?」まで証明させるんだ。

おとなのことばHAIP:Wallet Attestation(クライアント認証)と Key Attestation(WSCD 等での鍵保管証明)が MUST。素の OID4VCI ではいずれも任意。
HAIP・共通

フォーマットとアルゴリズムを 固定する

HAIP が固定する値
フォーマット: dc+sd-jwt(SD-JWT VC) または mso_mdoc(mdoc)
             # ウォレットは両対応。素の仕様はフォーマット非依存(自由)
署名      : ES256(P-256)を最低サポート
ハッシュ  : SHA-256
Issuer鍵解決: X.509(x5c に証明書チェーン。自己署名ダメ)

はいぷ先生素の仕様は「どんな形式・どんな算法でもいいよ」と自由。でも自由すぎるとつながらない。HAIP は「これを使え」と1つに決めて、相互運用を保証するんだ。

おとなのことばHAIP:SD-JWT VC(dc+sd-jwt)/ mdoc(mso_mdoc)の少なくとも一方、ES256/P-256、SHA-256、X.509 鍵解決が MUST。素の OID4VCI/VP はいずれも規定せずプロファイルに委譲。
HAIP・検証①

検証者の依頼書に「署名と身元」を必須化

素の OID4VP → HAIP(依頼書)
# 素:client_id は複数方式から選べる／署名は方式次第
# HAIP:
  "client_id": "x509_hash:Uvcpq0Yn6...",   # ← x509_hash のみ必須
  署名付きリクエスト(JAR)＋ x5c で身元証明   # ← 必須
  クエリは DCQL のみ(presentation_definition 廃止)

はいぷ先生素だと検証者の名乗り方は何通りもある。HAIP は x509_hash に一本化し、依頼書に必ず署名させる。だからニセ検証者(フィッシング)にだまされにくい。

おとなのことばHAIP:client_id は x509_hash のみ MUST(x509_san_dns は廃止)、署名付きリクエスト(JAR)必須、DCQL 必須。素の OID4VP は複数プレフィックス可・署名可否はプレフィックス依存。
HAIP・検証②

答えは「まほうのふうとう」で暗号化して返す

HAIP の応答(暗号化必須)
response_mode = "direct_post.jwt"   # レスポンスを JWE で暗号化
JWE: { "alg":"ECDH-ES", "enc":"A128GCM/A256GCM", "epk":{...} }
検証者は認可リクエストごとに エフェメラル(使い捨て)鍵 を用意

はいぷ先生素だと vp_token をそのまま(平文で)返せる。HAIP は必ず暗号化して返す(第3話の「まほうのふうとう」)。しかも毎回ちがう鍵で、追跡もされにくい。

おとなのことばHAIP:direct_post.jwt によるレスポンス暗号化(ECDH-ES / A128GCM・A256GCM)と、認可リクエストごとのエフェメラル暗号鍵が MUST。素の OID4VP では暗号化は任意。
HAIP・検証③＋失効

「信頼できる発行者か」と「失効していないか」

HAIP が検証時に足すチェック
  • Trusted Authorities(aki):DCQL で「信頼する発行者(トラストアンカー)由来か」を絞り込む(必須)
  • Status List:Token Status List で失効していないか(exp と併用)
  • KB-JWT は holder binding のため常に必須(素は holder binding 時のみ)

検証者本物・本人・今回・宛先・中身OKに加えて、「信頼する発行者の証明書か」「失効していないか」まで確かめる。これで安心して受け入れられる!

おとなのことばHAIP:aki ベース trusted_authorities クエリ必須、Token Status List による失効確認、KB-JWT 常時必須。高保証の要件がそろいます。
