FAPI2 の しょうめいの ながれを おってみよう

✦ ✦

はいぷ先生だい3わでは FAPI2 が「ぎんこうの きびしい ルールブック」だと ならったね。だい4わでは、じっさいに どんな じゅんばんで、なにを おくりあって、どう けんさして いるかを、ステップごとに くわしく おってみよう!

おとなのことば本編は FAPI2 Security Profile が求める認可コードフローを、PAR(事前登録)→ PKCE(コード横取り防止)→ iss(発行者確認)→ DPoP(トークンを鍵に束縛)の順で追います。実際に送受信するパラメータと、受け取った側の検証内容を各ページに掲載します。

クライアントあなたの かわりに、けんさを うけて「きっぷ(トークン)」を もらい、まどぐちで しょうめいしょ(VC)を うけとる おつかいさん。

にんかサーバーほんにん確認や けんさを して、きっぷを はっこうする がかり。

リソースサーバーきっぷを かくにんして、しょうめいしょ(VC)を わたす まどぐち。

おとなのことばOAuth の役: Client(ウォレット)/ Authorization Server(トークンを発行)/ Resource Server(OID4VCI では Credential Endpoint)。あなた=Resource Owner(本人)。
だい4わ・その3

ぜんたいの ながれ(6ステップ)

  • 0
    じゅんび:PKCE の あいことばペア と DPoP の かぎペアを つくるクライアントが自分の中で 2 種類の秘密を用意
  • 1
    PAR:おねがいを こっそり さきに とうろく → うけとり番号(request_uri)Client ▶ AS(PARエンドポイント)
  • 2
    認可リクエスト:ブラウザで うけとり番号を みせて ログイン・どういClient ▶(ブラウザ)▶ AS
  • 3
    認可レスポンス:みじかい「ひきかえ券(code)」+ おくり主なふだ(iss)AS ▶ Client。iss を かならず確認
  • 4
    トークンリクエスト:code + あいことば + DPoP しょうめい → きっぷ(トークン)Client ▶ AS(トークンエンドポイント)
  • 5
    リソースアクセス:きっぷ + DPoP しょうめい で しょうめいしょ(VC)を うけとるClient ▶ Resource Server
おとなのことばこの後のページで各ステップの実際のメッセージと検証内容を1つずつ見ていきます。PAR=STEP1、PKCE=STEP0で用意しSTEP4で照合、iss=STEP3で確認、DPoP=STEP0で鍵生成・STEP4で束縛・STEP5で使用、という対応です。
STEP0 じゅんび①

PKCE:あいことばの ペアを つくる

クライアントの中だけで こっそり
クライアントが 自分で 生成(まだ 送らない)
# ① ながい ひみつの あいことば(自分だけが持つ)
code_verifier = dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

# ② ①を ハッシュ(SHA-256)した「合言葉の かげ」
code_challenge = E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
code_challenge_method = S256   # = BASE64URL(SHA256(verifier))

はいぷ先生いま おくるのは かげ(challenge)だけ。ほんものの あいことば(verifier)は てもとに かくしておく。あとで「かげと ぴったり あう あいことば」を だせるのは 本人だけ、というワザだよ。

おとなのことばPKCE(RFC7636)。code_verifier は高エントロピーの乱数。code_challenge = BASE64URL(SHA256(code_verifier))、method=S256。この時点では challenge のみを送り、verifier は STEP4 まで秘匿します。
STEP0 じゅんび②

DPoP:じぶんだけの かぎペアを つくる

＋
クライアントが 自分で 生成(秘密鍵は 外に 出さない)
# DPoP用の かぎペア(公開鍵 と 秘密鍵)
公開鍵 (jwk)  = { "kty":"EC", "crv":"P-256", "x":"l8t...", "y":"9VE..." }
秘密鍵        = (端末の 金庫の 中。ぜったいに 外に 出さない)

# この公開鍵から 計算できる「ゆびもん(thumbprint)」
jkt = 0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I

はいぷ先生この かぎペアが DPoP の しゅやく。あとで きっぷ(トークン)を この かぎに ひもづけして、「かぎを もつ本人だけ つかえる きっぷ」に するんだ。

おとなのことばDPoP(RFC9449)用の鍵ペア。秘密鍵はセキュアエレメント等に保管。公開鍵の SHA-256 サムプリント jkt(JWK Thumbprint)が、後でトークンに刻まれる「束縛先の指紋」になります。
STEP1

PAR:おねがいを こっそり さきに とうろく

▶POST /par(うらぐち)
① クライアント ▶ 認可サーバーPOST /par
response_type=code
client_id=s6BhdRkqt3
redirect_uri=https://wallet.example.org/cb
scope=employee_credential
state=af0ifjsldkj
code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
code_challenge_method=S256
# ↓ クライアント認証(FAPI2で必須。例: 鍵で署名した証明)
client_assertion_type=...jwt-bearer
client_assertion=eyJhbGciOiJFUzI1Ni...(署名JWT)
← 認可サーバーの おへんじ201 Created
{ "request_uri": "urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c",
  "expires_in": 60 }
おとなのことばPAR(RFC9126)。認可リクエストの全パラメータを、ブラウザを経由せずサーバー間で直接・認証付きで先に登録。AS は内容を保存し、短命の request_uri を返します。ブラウザの URL にパラメータを晒さないので改ざん・盗み見・肥大化を防止。
STEP2

認可リクエスト:うけとり番号を みせて ログイン

▶ブラウザ▶
② ブラウザ ▶ 認可サーバーGET /authorize
# URLには もう「うけとり番号」と client_id しか のせない!
GET /authorize?client_id=s6BhdRkqt3
  &request_uri=urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c

にんかサーバーうけとり番号だね。中身は さっき とうろく済み。では 本人ログインと 「この しょうめいしょを わたして いい?」の どういを おねがい。

おとなのことばFAPI2/HAIP では認可リクエストは PAR の request_uri 参照のみ。実際の要求内容はすべて AS 側に保存済みなので、ブラウザ経由でパラメータが渡らず安全。ここでユーザー認証と同意(consent)が行われます。
STEP3

認可レスポンス:ひきかえ券(code)+ おくり主なふだ(iss)

▶
③ 認可サーバー ▶ クライアント302 Redirect
https://wallet.example.org/cb?code=SplxlOBeZQQYbYS6WxSbIA
  &state=af0ifjsldkj
  &iss=https://as.example.com   # ← だれが おくったかの なふだ
クライアントが すぐに 確認すること
  • iss が「さいしょに おねがいした 認可サーバー」と 一致するか(ニセ AS に だまされていないか)
  • state が じぶんが 送った 値と 一致するか(CSRF 対策)
おとなのことばcode は短命の引換券(=認可コード)。iss(RFC9207)で応答元の AS を明示し、クライアントは期待した issuer と一致するか照合。複数 AS を扱うときのミックスアップ攻撃(ニセ AS に code を渡させる攻撃)を防ぎます。
STEP4(おくる)

トークンリクエスト:code + あいことば + DPoP しょうめい

▶POST /token
④ クライアント ▶ 認可サーバーPOST /token
# HTTPヘッダに DPoPしょうめい(公開鍵入りの署名JWT)を のせる
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2Iiwiandr...
   ├ ヘッダ: { "typ":"dpop+jwt","alg":"ES256","jwk":{公開鍵} }
   └ 中身:   { "htm":"POST", "htu":"https://as.example.com/token",
              "iat":1562262616, "jti":"-BwC3ESc6acc2lTc" }

# 本文
grant_type=authorization_code
code=SplxlOBeZQQYbYS6WxSbIA
redirect_uri=https://wallet.example.org/cb
code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk  # ← 本物の あいことば!

クライアントここで はじめて 本物の あいことば(code_verifier)と、DPoPの かぎで 署名した しょうめいを いっしょに だすよ。

おとなのことばDPoP proof は毎回作る署名 JWT。htm(メソッド)/htu(宛先URL)/iat/jti(使い捨て ID)を含み、ヘッダの jwk に公開鍵を同梱。これで「この鍵の持ち主が、この宛先へ、今」要求していることを証明します。
STEP4(けんさ)

認可サーバーの けんさ(PKCE照合 + DPoP検証)

じっくり チェック
認可サーバーが 確認すること
  • PKCE照合: BASE64URL(SHA256(code_verifier)) が、STEP1で 預かった code_challenge と ぴったり一致するか → 一致すれば「code を横取りした別人ではない」
  • code が 有効(未使用・期限内・この client 宛)か
  • DPoP検証: DPoP proof の 署名が ヘッダの jwk(公開鍵)で 正しく 検証できるか。htm/htu が この要求(POST /token)と 一致、jti が 使い回しでないか

にんかサーバーあいことばの かげ と 本物が ぴったり! DPoPの 署名も 本物! よし、この DPoP鍵に ひもづけた きっぷを はっこうしよう。

おとなのことばPKCE 照合(SHA256(verifier)==challenge)で認可コード横取りを無効化。DPoP proof の署名・htm/htu・jti 検証を通過したら、AS は proof の公開鍵から jkt を計算し、次ステップでトークンに束縛します。
STEP4(うけとる)

DPoP束縛トークンの はっこう

▶▶
← 認可サーバー ▶ クライアント200 OK
{ "token_type": "DPoP",            # ← ただの Bearer ではない!
  "access_token": "eyJhbGci...(中に cnf.jkt が 刻まれている)",
  "expires_in": 300 }

# アクセストークンの中身(発行者が署名):
  "cnf": { "jkt": "0ZcOCORZNYy-DWpqq30jZyJGHTN0d2HglBV3uiguA4I" }
        └ = STEP0で作った DPoP公開鍵の ゆびもん。これで きっぷが 鍵に 束縛される

はいぷ先生この きっぷ(トークン)には DPoP鍵の ゆびもん(jkt)が 刻まれた。だから その かぎを もつ 本人しか つかえない。ひろっても・ぬすんでも つかえない きっぷだよ!

おとなのことばtoken_type: DPoP の送信者制約(sender-constrained)アクセストークン。トークン内(または introspection 応答)の cnf.jkt に DPoP 公開鍵のサムプリントが入り、以降の利用時に鍵の一致確認が必須になります。
STEP5(おくる)

リソースアクセス:きっぷ + あたらしい DPoP しょうめい

▶POST /credential
⑤ クライアント ▶ リソースサーバーPOST /credential
# きっぷは「DPoP」スキームで のせる(Bearerではない)
Authorization: DPoP eyJhbGci...(さっきの access_token)

# あたらしい DPoPしょうめい(宛先が まどぐちに 変わる & ath が 増える)
DPoP: eyJ0eXAiOiJkcG9wK2p3dCIsImFsZyI6IkVTMjU2Ii...
   └ 中身: { "htm":"POST", "htu":"https://issuer.example.com/credential",
             "iat":1562262618, "jti":"e1j3V_bKic8-LAEB",
             "ath":"fUHyO2r2Z3DZ53EsNrWBb0xWXoaNy59IiKCAqksmQEo" }
                   └ ath = きっぷ(access_token)の ハッシュ
おとなのことば利用時は Authorization: DPoP <token> と、その要求専用の新しい DPoP proof をセット。proof には ath(アクセストークンの SHA-256 ハッシュ)が加わり、宛先 htu はリソースサーバーになります。(サーバーが要求すれば nonce も含める)
STEP5(けんさ)

リソースサーバーの けんさ(鍵の 束縛確認)

きびしく チェック
リソースサーバーが 確認すること(ぜんぶ 通れば VC を わたす)
  • access_token が 有効(署名/introspection、期限、scope)か
  • DPoP proof の 署名が ヘッダの jwk で 検証できるか
  • 束縛の 一致: きっぷの中の cnf.jkt と、DPoP proof の 公開鍵の ゆびもんが 同じか → ちがえば「鍵を もたない 別人」= 拒否
  • ath が この access_token の ハッシュと 一致するか(きっぷの すり替え防止)
  • htm/htu が この要求(POST /credential)と 一致、jti が 使い回しでないか

リソースサーバーきっぷの ゆびもん と、いま みせられた かぎの ゆびもんが ぴったり一致! ほんものの もちぬしだ。しょうめいしょ(VC)を どうぞ!

おとなのことば核心は cnf.jkt(トークンに刻まれた指紋)== DPoP proof の公開鍵サムプリントの照合。ここが一致しないと、たとえトークンを盗んでも(対応する秘密鍵がないため)proof を作れず使えません。ath でトークンと proof の結び付きも確認します。
だい4わ・まとめ

どの ワザが なにを まもったか

ワザいつふせぐ こと(まもる もの)
PARSTEP1リクエストの 改ざん・盗み見・肥大化(ブラウザに パラメータを 晒さない)
PKCESTEP0で用意→STEP4で照合認可コードの 横取り(verifierを持つ本人だけが トークン交換できる)
issSTEP3ミックスアップ攻撃(ニセ認可サーバーへの 誘導)
DPoPSTEP0で鍵→STEP4で束縛→STEP5で使用トークンの 盗難悪用(鍵を持つ本人だけが トークンを使える)

はいぷ先生4つの ワザが それぞれ ちがう 攻撃を ふさぐ。だから FAPI2 は「ぎんこう なみに あんぜん」なんだ。HAIP は これを VC発行にも もとめている、というわけ!

つぎのステップ正確な要件レベルは docs/09(読み合わせコンパニオン)の PAR / PKCE / iss / DPoP 行、概念の やさしい導入は docs/10(第3話)を参照。サンプル値は RFC 7636 / RFC 9449 の例に準拠。おつかれさまでした! 🎉
