# ⑥ OID4VC/OID4VP 仕様相談・開発相談エージェントの作り方(Claude Projects 版)

> **目的**: OID4VCI / OID4VP / HAIP について、**仕様の疑問にも、実装の相談にも答えられるチャット相手**を作る。
>
> **方式**: [Claude Projects](https://claude.ai/) を使う。エンジニア以外(企画・営業・新入社員)も含め、ブラウザでチャットするだけでアクセスできる社内相談窓口として運用する。
>
> **前提**: このリポジトリの `docs/01`〜`05` を「知識(ナレッジ)」として Project に登録し、`docs/03` で得た**一次情報確認の姿勢**をそのままエージェントの振る舞いに引き継がせます。

## 1. Claude Projects とは / なぜこの方式か

**Claude Projects** は、claude.ai 上で作れる「特定用途に特化したチャット空間」です。以下の 2 つを設定できます。

| 設定項目 | 役割 |
|---|---|
| **Project knowledge(ナレッジ)** | ファイル(Markdown / PDF / テキスト等)をアップロードしておくと、そのプロジェクト内の会話で常に参照される |
| **Custom instructions(カスタム指示)** | そのプロジェクトの「振る舞い方(ペルソナ・回答方針・注意点)」を指定する、いわば専用のシステムプロンプト |

新しいチャットを始めるたびに知識やキャラ設定を説明し直す必要がなく、**「ブラウザを開いて質問するだけ」で同じ品質の回答が得られる**のが利点です。エンジニア以外の社員でも使えるハードルの低さが、この用途(社内での仕様相談窓口)に合っています。

> 💡 前提条件: Claude Projects の利用には Claude の有料プラン(Pro / Team / Enterprise 等)が必要です。すでにご利用中の契約プランで Projects 機能が使えるかは、claude.ai の設定画面でご確認ください。

## 2. セットアップ手順

1. [claude.ai](https://claude.ai/) にログイン → 左サイドバーの **「Projects」** → **「Create project」**
2. プロジェクト名・説明を入力
   - 名前の例: `OID4VC/OID4VP 相談室`
   - 説明の例: `OID4VCI・OID4VP・HAIP の仕様確認や実装相談ができます`
3. **「Project knowledge」** に、下記 [§4](#4-アップロードするナレッジファイル) のファイルをアップロード
4. **「Custom instructions」**(または「Set custom instructions」)に、下記 [§3](#3-custom-instructionsそのまま貼り付け用) のテキストをそのまま貼り付けて保存
5. (可能であれば)チャット画面の **Web 検索(Web search)機能を有効化**しておく
   - 理由: OID4VCI/OID4VP/HAIP は**ドラフトが頻繁に改訂される仕様**です(本リポジトリ作成中も draft-04→05→06→Final で内容が変わったことを実際に確認済み)。アップロードした docs は「ある時点のスナップショット」なので、**最新情報が必要な質問には Web 検索で一次情報(openid.net)を確認させる**運用が安全です
6. プロジェクト内で新しいチャットを開始し、[§5](#5-動作確認プロンプト集) のプロンプトで動作確認

## 3. Custom Instructions(そのまま貼り付け用)

以下をそのまま Custom Instructions 欄にコピー&ペーストしてください。

```
あなたは、社内の OID4VCI / OID4VP / HAIP(OID4VC Hype)の「仕様相談・開発相談」に応じる専門アシスタントです。

## 対象範囲
- OID4VCI(OpenID for Verifiable Credential Issuance)/ OID4VP(OpenID for Verifiable Presentations)
- HAIP(OpenID4VC High Assurance Interoperability Profile)
- 関連仕様: SD-JWT / SD-JWT VC / ISO mdoc / IETF Token Status List / DID
- 認可サーバー実装(Authlete 等)との関係
- 当社の VC 発行・VP 検証基盤の設計・実装相談
- 関連トピックとして AI エージェント(MCP/A2A/AP2/UCP)にも簡単に答えられるが、専門は上記の VC/VP 領域

## 回答の基本方針
1. **相手のレベルに合わせる**: 質問者が初心者そうであれば、専門用語は避けるか、使ったら一言で説明を添える。エンジニアからの実装相談には、具体的なパラメータ名・JSON例・コード相当の粒度で答える。
2. **登場人物ベースで整理する**: フローや仕組みを説明するときは、できるだけ「登場人物(Issuer/Holder/Verifier 等)」「その属性」「できること」「やること」「使う道具(パラメータ・エンドポイント)」「なぜそれが必要か」という切り口で構造化する。表形式が読みやすい場合は表を使う。
3. **確度を必ず区別する**: 回答の中で以下を明確に区別すること。
   - 「Project knowledge(docs/01〜05)で確認済みの情報」
   - 「一般的な仕様知識としては合っているはずだが、一次情報未確認の情報」
   - 「不確かな情報・推測」
   曖昧なまま断定しない。特にバージョン依存の細部(MUST/SHOULD の区別、パラメータ名、draft と Final の差分)は、自信がない場合は「要確認」と明記する。
4. **仕様は変わり続けている前提で話す**: OID4VCI/OID4VP/HAIP はドラフトが頻繁に改訂されてきた仕様です。「最新のドラフトではどうか」「Final ではどうか」を聞かれたら、Web 検索が使える場合は openid.net の一次情報を確認してから答える。確認できない場合は、いつ時点の情報かを明示する。
5. **実装相談では一次情報へのリンクを示す**: 「この要件は本当に必須か」を尋ねられたら、可能な範囲で該当仕様書のセクションや RFC 番号を示す。

## 話し方
- 日本語で、丁寧だが簡潔に。
- 新入社員向けの説明を求められたら、docs/04 の紙芝居のような比喩(登場人物になぞらえた説明)も使ってよい。
- 質問が曖昧な場合は、的確な回答のために一つだけ確認の質問をしてよい(聞きすぎない)。

## やってはいけないこと
- 未確認の MUST/SHOULD 要件を、確認済みであるかのように断定しない。
- 存在しないパラメータ名・URLを作り話しない(わからない場合は「わからない」と言う)。
- OID4VC と無関係な話題(一般的なプログラミング相談等)は、対象範囲外である旨を伝えた上で、簡潔に対応する程度に留める。
```

## 5. 動作確認プロンプト集

セットアップ後、以下のような質問を投げて挙動を確認してください。

1. 「OID4VCI と OID4VP の違いを新入社員に説明して」→ 基礎ドキュメントの内容が反映されているか
2. 「HAIP で `client_id` に使えるプレフィックスは何?」→ `x509_hash:` のみが MUST という**確定情報**として答えるか(かつ出典への言及があるか)
3. 「HAIP の最新のドラフトでは何が変わった?」→ Web 検索が有効なら openid.net を確認しにいくか、無効なら「アップロード時点の情報である」旨を明示するか
4. 「Pre-Authorized Code Flow は HAIP で必須?」→ 「MUST ではない」と正確に答えるか(この論点は本セッションで実際に確認したもの)
5. 「うちの Verifier 実装で `presentation_definition` を使ってるんだけど、HAIP 対応でどう直せばいい?」→ 開発相談として、DCQL への移行方針を具体的な JSON 例つきで答えるか

## 6. 運用・メンテナンス

- **仕様の改訂を追う**: HAIP は 1.0 Final(2025-12)の後、**v1.1 が 2026-12-21 公開予定**として作業項目化されています。OID4VCI/OID4VP 側にも今後の改訂があり得ます。四半期に一度など、一次情報(openid.net、GitHub の `openid/OpenID4VC-HAIP` 等)を確認し、`docs/01`〜`05` を更新のうえ、**Project knowledge を再アップロード**してください
- **ズレの早期発見**: 「このエージェントの回答、仕様書と違う気がする」と感じたら、`docs/03` の冒頭にあるような「検証履歴」の書き方に倣って、確認結果をドキュメントへ書き戻す運用にすると、ナレッジの精度が下がっていきません
- **社内フィードバックの吸い上げ**: 「よく聞かれる質問」が溜まってきたら、`docs/02`(対外説明資料)の FAQ セクションに反映すると、エージェントの回答品質も自然に上がります

## 7. 限界と、次のステップ(発展形)

Claude Projects 方式は「知識(静的なテキスト)+ 振る舞い方の指示」の組み合わせのため、以下はできません。

| できないこと | 理由 | 対応したい場合 |
|---|---|---|
| 自社の実装コード(発行基盤・検証基盤)を直接読んで相談に乗る | Project knowledge はリポジトリと接続されていない | **Claude Code のサブエージェント**(このセッションで使っている方式)を、実装コードを含むリポジトリ上に用意する |
| Slack から気軽に呼び出す | claude.ai のブラウザ利用が前提 | **Claude in Slack(Claude Tag)** の導入を検討 |
| 仕様書 PDF を都度自動で最新化する | Project knowledge は手動アップロード | 定期メンテナンス運用(§6)でカバー、または API + RAG のカスタム構築 |

まずは今回の Claude Projects 版で「仕様相談・開発相談」の需要と使われ方を見てみて、**実装コードまで踏み込んだ相談が頻発するようなら、Claude Code のサブエージェント化**を検討する、という段階的な進め方をおすすめします。
