第6話・その1

VC を VP に「変身」させよう

✦✦

はいぷ先生今日は少し本格的だよ。おさいふの中の VC(証明書)を、検証者に見せる VP(提示物)へ変身させる手順を、1ステップずつくわしく見ていこう。とくに KB-JWT の作り方は、細かく分解して説明するよ!

おとなのことば本編は SD-JWT VC を OID4VP で提示する処理を詳解します。中心は 選択的開示と KB-JWT(Key Binding JWT)の生成。サンプルは SD-JWT / SD-JWT VC 仕様の記法に沿ったダミー値です。

第6話・その2

登場人物と、VC・VP のちがい

持ち主のウォレット
(あなた)
検証者
(見せられる相手)

ウォレットぼくは VC(証明書)を持っている。発行者が署名した、本物のデジタル証明書だよ。

検証者わたしは、その証明書を「本物か」「本人か」確かめる係。ただし、全部は見せなくていい。必要な分だけでいいよ。

おとなのことばVC=発行者署名つきの証明書。VP=VC から必要な部分だけを選び、「持ち主本人が・この検証者に・今」提示していることの証明(KB-JWT)を付けたパッケージ。役:Holder(ウォレット)/ Verifier(検証者)。
第6話・その3

きょうのゴールと、全体の地図(9ステップ)

  • 0
    VC の中身(構造)を知る発行者JWT ＋ 開示(部品)＋ _sd_alg ＋ cnf(持ち主の鍵)
  • 1
    検証者から nonce と aud を受け取る「今回だけの合言葉」と「誰に見せるか」
  • 2
    選択的開示:見せる開示だけ選ぶ見せない部品は外す
  • 3
    提示のもとを組み立てる発行者JWT〜選んだ開示〜(末尾チルダまで)
  • 4〜5
    その文字列から sd_hash を計算バイト列 → ハッシュ → Base64url
  • 6〜8
    KB-JWT を作る(ペイロード→ヘッダ→署名)持ち主の秘密鍵で署名
  • 9
    連結して VP 完成 → 検証者が検証発行者JWT〜選んだ開示〜KB-JWT
おとなのことばこの地図の順に、次ページから具体化します。KB-JWT の材料(sd_hash)は「提示物そのもののハッシュ」なので、すり替え検知に効きます。
STEP0 ①

VC の構造:チルダ(~)で つながった部品

発行者JWT署名つき本体
~
開示1氏名
~
開示2生年月日
~
開示320歳以上
~

はいぷ先生SD-JWT VC は、「発行者が署名した本体」と、いくつもの 「開示(かいじ)= 部品」を、チルダ(~)でつないだ形をしているんだ。部品は取り外しできる。だから「必要な部品だけ見せる」ができるんだよ。

おとなのことばSD-JWT の Compact serialization:<Issuer署名JWT>~<Disclosure1>~<Disclosure2>~…~。発行時は全 Disclosure が付き、末尾はまだ KB-JWT なし(または空)。各要素は Base64url 文字列です。
STEP0 ②

本体(発行者JWT)の中身

発行者JWT の ペイロード(発行者が署名)
{
  "iss": "https://issuer.example.com",   # だれが発行したか
  "vct": "https://credentials.example.com/identity",
  "_sd_alg": "sha-256",                 # ★開示のハッシュに使う算法
  "_sd": [ "X9yH0Ajrdm1O...", "s0BKYsLWxQ...", "Dy-RYwZfaa..." ],
                                    # ↑隠した属性の「ハッシュ値」だけが並ぶ
  "cnf": { "jwk": { "kty":"EC","crv":"P-256","x":"...","y":"..." } },
                                    # ★持ち主の公開鍵(あとで超重要)
  "exp": 1798761600                    # 有効期限
}

はいぷ先生ポイントは3つ。_sd_alg=ハッシュの算法、_sd=隠した属性のハッシュ、cnf=持ち主の公開鍵。この cnf が「この証明書は誰のものか」を決めているよ。

おとなのことば_sd には各属性のダイジェスト(ソルト付きハッシュ)のみが入る。cnf.jwk の公開鍵が Holder Binding の要で、後で KB-JWT の署名検証に使われます(持ち主しか提示できない)。
STEP0 ③

「開示(部品)」の中身と、ハッシュのしくみ

開示3(Base64url を もどした中身)
[ "2GLC42sKQveCfGfryNRN9w", "age_over_20", true ]
   └ ソルト(毎回ちがう乱数)  └名前     └値

# この開示を まるごと ハッシュ(sha-256)→ Base64url すると…
  → "Dy-RYwZfaa..."   # 本体の _sd の中の1つと ぴったり一致!

はいぷ先生開示は [ソルト, 名前, 値] の3点セット。これをハッシュすると、本体の _sd にある値と一致するんだ。だから「本体の署名をこわさずに、部品を後から見せる」ことができる。渡さなかった部品は、ハッシュからは元にもどせない(ソルトがあるから当てられない)。

おとなのことばDisclosure = base64url(JSON([salt, claim_name, claim_value]))。検証者は受け取った各 Disclosure を同じ算法でハッシュし、_sd 内の値と突き合わせて属性を復元します。ソルトにより未開示属性は推測不能(データ最小化)。
STEP1

検証者からの依頼:nonce と aud

検証者 → ウォレット(提示のお願い)
{
  "nonce": "1234567890abcdef",         # 今回だけの合言葉(使い捨て)
  "aud":   "https://verifier.example.org", # だれ宛の提示か(=検証者)
  "ほしい属性": "age_over_20 だけでOK"
}

検証者「今回だけの合言葉(nonce)」と「わたし宛(aud)」を渡すね。この2つを、あとで作る証明に必ず入れてね。

おとなのことばnonce(リプレイ防止のチャレンジ)と aud(提示先=検証者の識別子)。OID4VP では認可リクエストで渡されます。これらを KB-JWT に入れることで「このセッション・この相手専用」の提示になります。
STEP2

選択的開示:見せる部品だけ選ぶ

発行者JWT
~
開示1 氏名見せない→外す
~
開示2 生年月日見せない→外す
~
開示3 20歳以上これだけ見せる
~

ウォレット検証者は「20歳以上か」だけ知りたい。だから 開示3(age_over_20)だけ残して、氏名や生年月日の部品は 外すよ。これで「20歳以上」だけ伝わる。

おとなのことば選択的開示=見せる Disclosure だけを残し、他は連結から除外。除外された属性は _sd にハッシュしか残らないため、値は検証者に伝わりません。
STEP3〜 導入

KB-JWT って何を証明するの?

はいぷ先生KB-JWT(Key Binding JWT)は、持ち主が 自分の秘密鍵でサインした小さな証明書。これ1枚で、次の4つを同時に証明するんだ:

① 本人(cnf の鍵の持ち主)/ ② この検証者宛(aud)/ ③ 今回の提示(nonce)/ ④ 中身のすり替えなし(sd_hash)

おとなのことばKB-JWT は Holder が cnf に対応する秘密鍵で署名。nonce(リプレイ防止)・aud(横流し防止)・sd_hash(提示物の同一性)・iat(時刻)を含みます。次ページから作成手順を分解します。
STEP3

まず「提示のもと」を組み立てる

発行者JWT
~
開示3(20歳以上)
~
KB-JWTまだ付けない!
ハッシュの対象になる文字列(これを覚えておく)
eyJ0eXAiOiJkYytzZC1qd3QiLCJhbGci...(発行者JWT)...~WyIyR0xDNDJzS...(開示3)...~
                                                        ↑末尾のチルダ(~)まで含める。KB-JWTは含めない

はいぷ先生KB-JWT を作る前に、「発行者JWT 〜 選んだ開示 〜」という文字列を用意する。末尾のチルダまで入れて、KB-JWT はまだ付けない。この文字列が、次のハッシュの材料になるよ。

おとなのことばハッシュ対象は「Issuer-JWT ＋ 選択した Disclosure 群を ~ で連結し、末尾に ~ を付けた文字列」。KB-JWT 自身は含めません(まだ存在しないため)。
STEP4

ハッシュの算法を確認する

発行者JWT の ペイロードを見る
  "_sd_alg": "sha-256"   # ← これを使え、という指定

ウォレットどのハッシュ算法を使えばいいかは、自分で勝手に決めない。本体のペイロードの _sd_alg に書いてある通り(ここでは sha-256)を使うよ。

おとなのことばハッシュ算法は SD-JWT の _sd_alg クレームで規定されます(HAIP では SHA-256 が必須)。Disclosure のダイジェストも sd_hash も、同じ算法で計算します。
STEP5

sd_hash を計算する(3つの変換)

🔤
① バイト列にする「提示のもと」文字列を ASCII/UTF-8 のバイトにする
→
🧮
② ハッシュ化_sd_alg(=SHA-256)でハッシュする(32バイトの値)
→
🔡
③ 符号化Base64url で文字にする = sd_hash
けっか
sd_hash = "Dy-RYwZfaaoC3inJbLslgPvMp09bH-clYP_3qbRqtW4"
きみの理解チェック「それ以前のものをバイナリ化 → ハッシュ → Base64」という理解はほぼ正解! 追加の注意は2つだけ:(1) ハッシュ対象は「選んだ開示だけ」を連結した文字列(見せない開示は入れない)。(2) KB-JWT 自身は含めない(末尾チルダまで)。この2点を守れば完璧です。
おとなのことばsd_hash = base64url( SHA-256( ASCIIバイト列(<Issuer-JWT>~<選択Disclosure>~) ) )。提示物そのもののダイジェストなので、途中で1文字でも改ざんされると検証時に不一致になります。
STEP6

KB-JWT の「ペイロード(中身)」を作る

KB-JWT ペイロード
{
  "nonce":   "1234567890abcdef",                 # STEP1で受け取った合言葉
  "aud":     "https://verifier.example.org",     # STEP1で受け取った宛先
  "iat":     1735689600,                         # 今の時刻
  "sd_hash": "Dy-RYwZfaaoC3inJbLslgPvMp09bH-clYP_3qbRqtW4" # STEP5の値
}

はいぷ先生さっき計算した sd_hash と、検証者からもらった nonce・aud、それに今の時刻 iat を合わせて、ペイロードを作る。これで「今・この相手・この中身」が全部そろったね。

おとなのことばKB-JWT の必須クレーム:iat / aud / nonce / sd_hash。検証者はこれらを自分の発行値・自分の識別子・提示物のハッシュと突き合わせます。
STEP7

KB-JWT の「ヘッダ」を作る

KB-JWT ヘッダ
{
  "typ": "kb+jwt",   # これは「Key Binding 用の JWT」だという目印
  "alg": "ES256"     # 署名(と検証)に使う算法。P-256 の楕円曲線
}

ウォレットヘッダには「これは KB-JWT だよ(typ: kb+jwt)」という目印と、「この算法で署名するよ(alg: ES256)」を書く。検証者は alg を見て、同じ方法で署名を確かめられる。

おとなのことばKB-JWT ヘッダは typ: kb+jwt が必須(取り違え防止)。alg は Holder の署名アルゴリズム(HAIP では ES256/P-256)。検証時はこの alg と cnf.jwk で署名検証します。
STEP8

署名して KB-JWT を完成させる

🔡
① それぞれ符号化ヘッダとペイロードを Base64url に
→
🖊️
② 署名を計算ヘッダ.ペイロード を持ち主の秘密鍵で署名
→
🎫
③ 連結ヘッダ.ペイロード.署名 = KB-JWT 完成
できあがった KB-JWT(3つを ドット . でつなぐ)
eyJ0eXAiOiJrYitqd3QiLCJhbGciOiJFUzI1NiJ9  # ヘッダ(Base64url)
.eyJub25jZSI6IjEyMzQ1Njc4OTBhYmNkZWYiLCJhdWQiOiJodHRwczov...  # ペイロード
.MEUCIQDf...署名...  # 秘密鍵での署名
ここが Key Binding の核心署名に使うのは 持ち主の秘密鍵。その公開鍵は VC 本体の cnf に入っている(STEP0②)。だから検証者は「cnf の鍵で署名が確かめられる=本物の持ち主」と判断できます。鍵を持たない人は KB-JWT を作れません。
おとなのことばJWT の署名対象は base64url(header) + "." + base64url(payload)。これを Holder の秘密鍵で署名し、.signature を連結して JWS(=KB-JWT)完成。検証は cnf.jwk の公開鍵で行います。
STEP9

連結して VP 完成!

✦✦
発行者JWT
~
開示3(20歳以上)
~
KB-JWT持ち主の証明

はいぷ先生最後に、さっきの「提示のもと」の末尾チルダのうしろに KB-JWT を連結する。これで VP(提示物)の完成! これを検証者に渡すよ。

おとなのことば提示形式:<Issuer-JWT>~<選択Disclosure>~<KB-JWT>。OID4VP ではこれを vp_token として(HAIP では暗号化して)検証者へ送ります。
STEP9(検証)

検証者は こう確かめる

受け取った VP のチェック(全部OKなら合格)
  • 発行者の署名:発行者JWT の署名を、発行者の公開鍵(証明書 x5c 等)で検証 → 本物の証明書か
  • 開示のハッシュ照合:受け取った各開示をハッシュ →本体の _sd にあるか → 属性を復元
  • KB-JWT の署名:本体の cnf の公開鍵で KB-JWT の署名を検証 → 本人か
  • sd_hash 一致:受け取った「発行者JWT〜開示〜」を自分でハッシュ → KB-JWT の sd_hash と一致するか(すり替え検知)
  • nonce / aud:自分が出した nonce・自分の識別子 aud と一致するか(リプレイ・横流し防止)
  • 期限・失効:exp と ステータスリストで、有効か・失効していないか

検証者ぜんぶ合格! 「本物の証明書」で「本人が」「わたし宛に」「今回」「20歳以上」を提示した、と確認できたよ。氏名や生年月日は知らないままでOK!

おとなのことば検証順序の一例:発行者署名 → Disclosure ダイジェスト照合 → KB-JWT 署名(cnf)→ sd_hash 再計算一致 → nonce/aud/iat → exp/status。1つでも失敗したら拒否します。
