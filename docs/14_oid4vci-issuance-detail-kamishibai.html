第7話・その1

証明書(VC)は こうして 発行される

✦✦

はいぷ先生第5話では発行の流れを「ざっくり」見たね。第7話はくわしく。とくに、ウォレットが「この鍵はぼくのだ」と示す proof(鍵所有証明)の作り方を、KB-JWT のときと同じように1ステップずつ見ていくよ。

おとなのことばOID4VCI の発行フローを詳解します。本編は HAIP でも使う 認可コードフローを軸に、Credential Offer → メタデータ → トークン → Nonce → proof JWT 生成 → Credential 受領 を扱います。サンプルは仕様の記法に沿ったダミー値です。
第7話・その2

発行者わたしは2つの窓口を持つ。「本人確認して きっぷを渡す窓口(認可サーバー)」と、「きっぷと引きかえに証明書を渡す窓口(Credential Endpoint)」だよ。

おとなのことば発行者(Issuer)は Authorization Server(トークン発行)と Credential Endpoint(VC 発行)を持ちます。ウォレットは OAuth の Client。あなたは Holder(持ち主)。
第7話・その3

全体の地図

  • 1
    Credential Offer:発行のおさそい(QR)どの発行者・どの証明書か
  • 2
    発行者メタデータ:窓口の場所と条件を知るcredential_endpoint / nonce_endpoint / 必要な proof
  • 3
    認可コードフロー:本人確認して code をもらうPAR＋PKCE(→第4話でくわしく)
  • 4
    トークン取得:code を アクセストークンに交換これで発行窓口に入れる
  • 5
    Nonce 取得:使い捨ての合言葉 c_nonceproof に入れる
  • 6
    proof(鍵所有証明)を作るウォレットの秘密鍵で署名
  • 7
    Credential 取得:トークン＋proof で VC をもらうすぐ出せなければ Deferred
おとなのことばproof の公開鍵が、発行される VC の cnf に入る(=第6話の「持ち主の鍵」)。だから発行フローと提示フローは 鍵で一本につながっています。
STEP1

Credential Offer(発行のおさそい)

QR/リンクの中身(Credential Offer)
{
  "credential_issuer": "https://issuer.example.com",
  "credential_configuration_ids": ["IdentityCredential"],
  "grants": {
    "authorization_code": { "issuer_state": "eyJ...state" }
  }
}

はいぷ先生おさそいには「どの発行者か」「どの証明書か」「どの入口(grants)を使うか」が書いてある。ここでは authorization_code(認可コードフロー)だね。

おとなのことばCredential Offer。grants に authorization_code があれば認可コードフロー。issuer_state は発行者がこの発行の文脈を紐づける値です。
STEP2

発行者メタデータ(窓口の案内図)

GET /.well-known/openid-credential-issuer
{
  "credential_endpoint": "https://issuer.example.com/credential",
  "nonce_endpoint":      "https://issuer.example.com/nonce",
  "credential_configurations_supported": {
    "IdentityCredential": {
      "format": "dc+sd-jwt",
      "scope": "identity_credential",
      "cryptographic_binding_methods_supported": ["jwk"],
      "proof_types_supported": { "jwt": { "proof_signing_alg_values_supported": ["ES256"] } }
    }
  }
}

ウォレット証明書の窓口(credential_endpoint)、合言葉の窓口(nonce_endpoint)、そして「proof は jwt 形式・ES256 で作ってね」という条件がわかった!

おとなのことばメタデータで各エンドポイントと、発行できる構成(format・scope・鍵バインディング方式・proof_types_supported)を確認。cryptographic_binding_methods_supported があるので proof（鍵所有証明）が必要とわかります。
STEP3

認可コードフローで「引きかえ券(code)」をもらう

  • A
    PAR:リクエストを裏口から先に登録 → request_uri大声で言わない
  • B
    ブラウザで request_uri を見せ、本人ログイン＋同意
  • C
    発行者から code ＋ iss が返るiss を必ず確認

はいぷ先生ここは第4話(FAPI2)でくわしくやった PAR＋PKCE と同じ。「本人だと確かめて、みじかい引きかえ券(code)を渡す」ステップだよ。

おとなのことば認可コードフロー:PAR で認可リクエストを事前登録 → 認可エンドポイントで認証・同意 → code 取得(iss 検証)。PKCE の code_verifier は次のトークン要求で使います(詳細は docs/11 第4話)。
STEP4

トークン取得(code → アクセストークン)

ウォレット → 発行者POST /token
grant_type=authorization_code
code=SplxlOBeZQQYbYS6WxSbIA
code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
← 発行者の返事200 OK
{ "access_token": "eyJhbGci...", "token_type": "Bearer", "expires_in": 300,
  "authorization_details": [ { "type":"openid_credential",
      "credential_configuration_id":"IdentityCredential",
      "credential_identifiers":["id-1"] } ] }
おとなのことばToken Endpoint。code と PKCE の code_verifier を送りアクセストークンを取得。authorization_details の credential_identifiers で、次に要求できる具体的なクレデンシャルが示されます。
STEP5

Nonce 取得(使い捨ての合言葉)

ウォレット → 発行者POST /nonce
(本文なし)
← 発行者の返事
{ "c_nonce": "wKI4LT4bLtclpz25a1zQ7Jm5oi8" }

ウォレットproof に入れる「今回だけの合言葉」をもらった。これで、あとで作る proof が「使い回し」できなくなる。

おとなのことばNonce Endpoint から c_nonce を取得。これを proof に入れることでリプレイ(再利用)を防ぎます。HAIP では鍵バインディング利用時に nonce_endpoint が必須。
STEP6(いちばん大事)

proof(鍵所有証明)を作る

proof JWT の ヘッダ と ペイロード
# ヘッダ:公開鍵を同梱する
{ "typ": "openid4vci-proof+jwt", "alg": "ES256",
  "jwk": { "kty":"EC","crv":"P-256","x":"l8t...","y":"9VE..." } }
# ペイロード
{ "aud": "https://issuer.example.com",   # だれ宛(発行者)
  "iat": 1735689600,
  "nonce": "wKI4LT4bLtclpz25a1zQ7Jm5oi8" }  # ← STEP5の c_nonce
🔡
① 符号化ヘッダとペイロードを Base64url
→
🖊️
② 署名ヘッダ.ペイロード をウォレットの秘密鍵で署名
→
🎫
③ 連結ヘッダ.ペイロード.署名 = proof 完成
KB-JWT と そっくり作り方は第6話の KB-JWT と同じ「ヘッダ＋ペイロード→署名→連結」。ちがいは、proof は発行時(aud=発行者・nonce=c_nonce)、KB-JWT は提示時(aud=検証者・sd_hash あり)という目的と中身だけ。ヘッダの jwk(公開鍵)が、この後 VC の cnf になります。
おとなのことばproof JWT:typ: openid4vci-proof+jwt、aud=Credential Issuer、nonce=c_nonce、ヘッダ jwk に公開鍵。ウォレットの秘密鍵で署名。この公開鍵が発行 VC の cnf に焼き込まれ Key Binding が成立します。
STEP7(送る)

Credential 取得の リクエスト

ウォレット → 発行者POST /credential
Authorization: Bearer eyJhbGci...(アクセストークン)

{ "credential_identifier": "id-1",
  "proofs": { "jwt": [ "eyJ0eXAiOiJvcGVuaWQ0dmNpLXByb29mK2p3dCI...(proof)" ] } }

ウォレットアクセストークン(きっぷ)と、さっき作った proof(鍵の証明)を一緒に出すよ。

おとなのことばCredential Endpoint へアクセストークン＋proofs を送信。credential_identifier(または credential_configuration_id)で対象を指定。proofs は複数形(バッチ発行に対応)。
STEP7(受け取る)

証明書(VC)、とうちゃく!

✦
← 発行者の返事200 OK
{ "credentials": [ { "credential":
    "eyJ0eXAiOiJkYytzZC1qd3QiLCJhbGciOiJFUzI1NiJ9.eyJfc2QiOls...~WyJfMjZi...~" } ] }

# 受け取った VC の中には…
  "cnf": { "jwk": { "kty":"EC","crv":"P-256","x":"l8t...","y":"9VE..." } }
        └ proof で示した公開鍵と同じ = この VC は このウォレット専用

はいぷ先生できた! 発行者が署名した VC(dc+sd-jwt)だ。中の cnf は、さっき proof で示した公開鍵。だから「この証明書は このウォレットの持ち主のもの」になったんだ。(第6話の提示につながるよ)

おとなのことばCredential Response の credentials に SD-JWT VC を受領。VC の cnf に proof の公開鍵が入り、以降の提示(VP)で KB-JWT の署名検証に使われます。
STEP7 の別パターン ＆ STEP8

すぐ出せない時 と、受け取り通知

すぐ出せない場合の返事(Deferred)
{ "transaction_id": "8xLOxBtZp8", "interval": 5 }
   └ この番号で、あとで Deferred Credential Endpoint に取りに行く
受け取り後:ウォレット → 発行者POST /notification
{ "notification_id": "3fwe98js", "event": "credential_accepted" }
おとなのことば即時発行できない場合は transaction_id を返し、後で Deferred Credential Endpoint で取得。保存の成否は Notification Endpoint で発行者へ通知できます。
