〜 VP提示・検証(OID4VP)の流れ:検証者の依頼から 合格判定まで 〜

第8話・その1

証明書(VC)を 検証者に 見せる しくみ

✦✦

はいぷ先生第6話では VC を VP に「変身」させる中身(KB-JWT)をやったね。第8話は、それをプロトコル(やり取りのルール)として見る。検証者の依頼から、ウォレットの応答、検証者の合格判定までの流れだよ。

おとなのことばOID4VP の提示フローを詳解します。検証者の Authorization Request(dcql_query/nonce/response_mode)→ ウォレットの vp_token 応答 → 検証。KB-JWT 生成の詳細は第6話(docs/13)を参照。
第8話・その2

登場人物と、全体の地図

検証者(Verifier)
ウォレット(Holder)
  • 1
    検証者が「依頼書」を出す何を見せてほしいか＝dcql_query、nonce、宛先
  • 2
    ウォレットが依頼書を読み、検証者の身元を確認
  • 3
    ユーザーが同意し、見せる属性を選ぶ(選択的開示)
  • 4
    ウォレットが vp_token を組み立てるVC＋選んだ開示＋KB-JWT(第6話)
  • 5
    応答モードに従って送るdirect_post など
  • 6
    検証者が検証 → 合格なら受け入れ
おとなのことばOID4VP は OAuth の認可リクエストを拡張し、アクセストークンの代わりに VP トークンを返させる仕組み。検証者=Client、ウォレット=Authorization Server の位置づけです。
STEP1

検証者の「依頼書」(Authorization Request)

検証者 → ウォレット(署名付きリクエスト)
{
  "client_id": "x509_hash:Uvcpq0Yn6...gAsr8B",  # 検証者の身元
  "response_type": "vp_token",
  "response_mode": "direct_post.jwt",
  "response_uri": "https://verifier.example.org/response",
  "nonce": "1234567890abcdef",           # 今回だけの合言葉
  "dcql_query": { ... 次のページ ... },
  "client_metadata": { "jwks": { ... 暗号化用の鍵 ... } }
}

検証者依頼書には「わたしは誰か(client_id)」「VPで返してね(vp_token)」「どこへどう送るか(response_mode/uri)」「今回の合言葉(nonce)」「何がほしいか(dcql_query)」を書くよ。

おとなのことばresponse_type=vp_token。client_id のプレフィックス(例 x509_hash)で検証者の身元検証方式が決まる。nonce は KB-JWT に入って戻ってきます。client_metadata にレスポンス暗号化用の鍵を載せます。
STEP1(つづき)

DCQL:「何がほしいか」の書き方

dcql_query(ほしい証明書と属性)
{
  "credentials": [
    { "id": "my_cred",
      "format": "dc+sd-jwt",
      "meta": { "vct_values": ["https://credentials.example.com/identity"] },
      "claims": [ { "path": ["age_over_20"] } ]   # 年齢だけ要求
    }
  ]
}

はいぷ先生DCQL(ディーシーキューエル)は「どの種類の証明書の、どの属性がほしいか」を書く専用の言葉。ここでは age_over_20 だけを要求している。古い presentation_definition は 1.0 で廃止され、DCQL に一本化されたよ。

おとなのことばDCQL(Digital Credentials Query Language)。credentials[].id が応答の vp_token のキーになります。format/meta/claims で対象と属性を指定。mdoc の場合は meta.doctype_value と namespace 単位の指定。
STEP2〜3

検証者の確認と、ユーザーの同意

ウォレットが 先に 確認すること
  • 依頼書の署名を検証者の証明書(x5c)で確認 → 本物の検証者か(ニセ検証者=フィッシング対策)
  • client_id と証明書が一致するか
  • 手元の VC で dcql_query に答えられるか

ウォレット本物の検証者だ。持っている「身分証 VC」で答えられる。ユーザーに「年齢(20歳以上)だけ見せていい?」と確認して、OK をもらうよ。

おとなのことば署名付きリクエスト(JAR)+ x5c チェーン検証で検証者の真正性を確認。ウォレットは要求内容をユーザーに提示し、同意(consent)を得てから提示します。
STEP4

vp_token を組み立てる

発行者JWT
~
開示(20歳以上)
~
KB-JWT
vp_token(DCQL の id をキーにした入れもの)
{
  "my_cred": [                # ← dcql_query の id
    "eyJ0eXAiOiJkYytzZC1qd3Qi...(発行者JWT)~WyIyR0xD...(開示)~eyJ0eXAiOiJrYitqd3Qi...(KB-JWT)"
  ]
}

はいぷ先生第6話でやった手順(選んだ開示＋KB-JWT)で提示物を作り、DCQL の id(my_cred)をキーにして入れる。presentation_submission はもう不要。マッチングがシンプルになったよ。

おとなのことばvp_token は DCQL の id をキーとする JSON オブジェクト(値は提示物の配列)。KB-JWT の nonce/aud/sd_hash 生成は第6話参照。
STEP5

応答モードに従って送る

ウォレット → 検証者(direct_post)POST /response
Content-Type: application/x-www-form-urlencoded

vp_token=%7B%22my_cred%22%3A%5B%22eyJ0eXAi...~...~...%22%5D%7D
state=af0ifjsldkj
応答モードの種類fragment(同一端末でブラウザに返す)/ direct_post(検証者サーバへ直接POST)/ direct_post.jwt(direct_post を暗号化)/ dc_api.jwt(ブラウザの Digital Credentials API 経由)。どれを使うかは依頼書の response_mode で決まります。
おとなのことばクロスデバイス(PCにQR→スマホで読む)では応答を検証者サーバへ直接送る direct_post 系を使います。HAIP は暗号化必須の direct_post.jwt(次話)。
STEP6

検証者の 合格判定

受け取った vp_token のチェック
  • 発行者署名:VC が本物か(発行者の鍵で検証、トラストアンカーまで)
  • 開示のハッシュ照合:受け取った開示が _sd にあるか → 属性を復元
  • KB-JWT 署名:VC の cnf の鍵で検証 → 本人か
  • sd_hash / nonce / aud:提示物のハッシュ一致・自分の nonce・自分宛か
  • 期限・失効:exp と Status List
  • DCQL 充足:要求した属性がそろっているか

検証者全部合格! 「本物の身分証」で「本人が」「わたし宛に」「今回」「20歳以上」を示した、と確認。氏名や生年月日は知らないままサービスを提供できるよ。

おとなのことば検証は「発行者署名 → Disclosure 照合 → KB-JWT 署名(cnf)→ sd_hash/nonce/aud → exp/status → DCQL 充足」。1つでも失敗なら拒否。
